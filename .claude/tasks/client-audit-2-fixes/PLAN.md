## 1. Goal

Phase A closes four permission holes. An org Owner can no longer give a role to someone who is not already an active member (O10), nor hand out Platform roles or Seller roles in a buyer org (S03). An approver can no longer approve or reject their own order while another approver exists (A05). An order placed by the only approver of an org is approved at once, with an "auto-approved" audit entry, instead of sitting in "Pending" forever (A01/A07).
Phase B: the solo bundle (Estimator + Executive Approver) can be assigned (N01); the Owner sees every project of the org (W10); JSON errors stop leaking paths and model names (S13); the partner dropdown that lists every org becomes an exact-name lookup (D21); a record in another org answers 404 instead of a "not a member" message (O05); signup sends the verification email and shows an inline team-size error (B06); delegation grants and delegated actions reach the audit log (L06).

### 10.1 A1 (MEDIUM) - an unused existing-account invite must not outlive its inviter's authority

Supersedes Architect ruling 5 in REVIEW.md ("accept as-is, follow-up") for the NEW accept flow only. Root cause: `Auth\InviteAcceptController::invitationFor()` (called by both `show` = GET review and `accept` = POST) never looks at `org_invites.invited_by`, and nothing lists or revokes pending invites.

**The rule (spec, not a patch).** In `invitationFor()`, keep the existing `abort_unless(invite exists AND user verified AND e-mail equal, 404)` first and unchanged. Then extend the existing "invalid invite" condition (used OR expired OR role no longer assignable) with `OR ! $this->inviterStillAuthorised($invite)`; the outcome is the existing `HttpResponseException(response()->view('auth.invite-invalid', [], 404))`: same status, same static page, no new message, no flash, no audit row.

```
private function inviterStillAuthorised(OrgInvite $invite): bool
{
    $inviterId = (int) $invite->invited_by;
    $orgId = (int) $invite->org_id;

    if (UniversalAdmin::is($inviterId)) {
        return true;
    }

    return $this->assignments->isActiveMember($inviterId, $orgId)
        && $this->permissions->checkPermission($inviterId, $orgId, 'user_management', 'F');
}
```

- Constructor gains `private readonly PermissionService $permissions` (container-resolved like `OrgAdminController`); imports `App\Services\Rbac\PermissionService` and `App\Support\Rbac\UniversalAdmin`. The helper is private to this controller: no new public service method, no new abstraction.
- `checkPermission` is the helper the controllers use (`OrgAdminController::requireOrgLevel` calls it with `user_management` / `F`). Group and level are exactly those of `POST org-admin/invite`. The org is `$invite->org_id`, never the session or `CurrentOrg` of the signed-in invitee.
- `isActiveMember` is needed in addition to `checkPermission` only for one case: `checkPermission` evaluates a delegate as the principal (`DelegationService::resolveEffectiveUserId`), so an inviter who has lost every own role but still holds an active delegation would pass `checkPermission` alone.
- **Universal-admin inviter (decision c).** The UA test comes FIRST and must not be routed through `checkPermission`: for a listed user `checkPermission` calls `UniversalAdmin::recordBypass`, which would write an `allowed_universal_admin` row with `user_id` = the inviter during the INVITEE's request, misattributing the action. The UA's bypass was already logged when the invite was created (`requireOrgLevel` -> `checkPermission` on `POST org-admin/invite`, plus `universal_assign_restricted_role` where it applied), so accept writes no additional row. A UA inviter therefore stays valid exactly as long as they are in `UNIVERSAL_ADMIN_USER_IDS` and have a verified e-mail (`UniversalAdmin::is`); removed from the list, unverified, or never listed and without a role, the invite is invalid. This is consistent with ARCHITECTURE 10b/4.5: "no exemption for accepting an invite" refers to the INVITEE; a UA invitee still needs the verified-e-mail match.
- **Delegate inviter.** Authority follows `checkPermission` semantics: an invite created by a delegate acting for an Owner is valid while the delegation is active AND the delegate still holds an own active role in the org; revoking or expiring the delegation, or removing the delegate, invalidates it. Invites made by a legacy non-member delegate (possible before task 3b) become invalid at accept; that is the intended fail-closed reading.
- **Inviter deleted (FK).** `org_invites.invited_by` is NOT NULL with `ON DELETE CASCADE`, so deleting the user deletes the invite row and the token answers the existing bare 404. No code needed; a test pins it. If an invite row ever survives with a dangling `invited_by`, the id-based rule fails closed (`isActiveMember` false). The rule uses ids, never the `invitedBy` relation, so it cannot null-dereference.
- **No leak.** The new condition runs only after the invitee's verified-e-mail equality check, so any other account still gets the identical bare 404 whatever the inviter's state; the invitee sees the same "Invite link invalid or expired" page as for an expired invite.
- **Both modes.** The check is inside the controller and the routes are unmapped open routes (OPEN_ROUTES), so audit and enforce behave identically; a 404 is not a 403, so `DenialRecorder` writes nothing.
- **Not changed (deliberate).** `Auth\InviteController::register` and `show` (guest new-hire register link), `OrgAdminController::generateInvite`, `OrgInvite`, routes, `route_permission_map.php`, `route-list.json`, views, mail, migrations, config, `AuditFindingsRound2Test`. Parity for the guest link is an optional follow-up (ARCHITECTURE 12 item 13 below), NOT part of this amendment.
- **Residual race, accepted.** The check runs in `invitationFor()` before the claim transaction; an inviter removed in the same few milliseconds is not caught. It is MariaDB/concurrency territory and is named in ARCHITECTURE 12 item 4 (10.4).

  7. (iii) Stale-session approvals: `OrderApprovalController::index` (:25) and `authorizeApprovalAction` (:88), and `CheckoutController` (:211, :231) compare the order's org with `CurrentOrg::sessionOrg()` (the raw session value for non-universal admins) while the permission check uses `CurrentOrg::id()` (falls back to the first active org when the session org is no longer valid).   8. (iv) Invited new hires are never marked verified: `Auth\InviteController::register` passes `email_verified_at => now()` but the column is not in `User::$fillable` (app/Models/User.php:34-41), so the account is created unverified, no `Registered` event fires, no verification mail is sent, and the user sits behind the `verified` middleware until they use "resend".   9. (v) Delegation deadlock between exactly two approvers: pool = {P, D} with an active delegation P -> D: P is blocked by the self-approval guard and D is treated as P (`selfIds` includes the principal) and gets the misleading "You cannot approve your own order ..." for P's order. ### 10.10 Risks / open questions
