## 1. Goal

Phase A closes four permission holes. An org Owner can no longer give a role to someone who is not already an active member (O10), nor hand out Platform roles or Seller roles in a buyer org (S03). An approver can no longer approve or reject their own order while another approver exists (A05). An order placed by the only approver of an org is approved at once, with an "auto-approved" audit entry, instead of sitting in "Pending" forever (A01/A07).
Phase B: the solo bundle (Estimator + Executive Approver) can be assigned (N01); the Owner sees every project of the org (W10); JSON errors stop leaking paths and model names (S13); the partner dropdown that lists every org becomes an exact-name lookup (D21); a record in another org answers 404 instead of a "not a member" message (O05); signup sends the verification email and shows an inline team-size error (B06); delegation grants and delegated actions reach the audit log (L06).

### 10.1 A1 (MEDIUM) - an unused existing-account invite must not outlive its inviter's authority

Supersedes Architect ruling 5 in REVIEW.md ("accept as-is, follow-up") for the NEW accept flow only. Root cause: `Auth\InviteAcceptController::invitationFor()` (called by both `show` = GET review and `accept` = POST) never looks at `org_invites.invited_by`, and nothing lists or revokes pending invites.

**The rule (spec, not a patch).** In `invitationFor()`, keep the existing `abort_unless(invite exists AND user verified AND e-mail equal, 404)` first and unchanged. Then extend the existing "invalid invite" condition (used OR expired OR role no longer assignable) with `OR ! $this->inviterStillAuthorised($invite)`; the outcome is the existing `HttpResponseException(response()->view('auth.invite-invalid', [], 404))`: same status, same static page, no new message, no flash, no audit row.

```
private function inviterStillAuthorised(OrgInvite $invite): bool
{
    $inviterId = (int) $invite->invited_by;
    $orgId = (int) $invite->org_id;

    if (UniversalAdmin::is($inviterId)) {
        return true;
    }

    return $this->assignments->isActiveMember($inviterId, $orgId)
        && $this->permissions->checkPermission($inviterId, $orgId, 'user_management', 'F');
}
```

- Constructor gains `private readonly PermissionService $permissions` (container-resolved like `OrgAdminController`); imports `App\Services\Rbac\PermissionService` and `App\Support\Rbac\UniversalAdmin`. The helper is private to this controller: no new public service method, no new abstraction.
- `checkPermission` is the helper the controllers use (`OrgAdminController::requireOrgLevel` calls it with `user_management` / `F`). Group and level are exactly those of `POST org-admin/invite`. The org is `$invite->org_id`, never the session or `CurrentOrg` of the signed-in invitee.
- `isActiveMember` is needed in addition to `checkPermission` only for one case: `checkPermission` evaluates a delegate as the principal (`DelegationService::resolveEffectiveUserId`), so an inviter who has lost every own role but still holds an active delegation would pass `checkPermission` alone.
- **Universal-admin inviter (decision c).** The UA test comes FIRST and must not be routed through `checkPermission`: for a listed user `checkPermission` calls `UniversalAdmin::recordBypass`, which would write an `allowed_universal_admin` row with `user_id` = the inviter during the INVITEE's request, misattributing the action. The UA's bypass was already logged when the invite was created (`requireOrgLevel` -> `checkPermission` on `POST org-admin/invite`, plus `universal_assign_restricted_role` where it applied), so accept writes no additional row. A UA inviter therefore stays valid exactly as long as they are in `UNIVERSAL_ADMIN_USER_IDS` and have a verified e-mail (`UniversalAdmin::is`); removed from the list, unverified, or never listed and without a role, the invite is invalid. This is consistent with ARCHITECTURE 10b/4.5: "no exemption for accepting an invite" refers to the INVITEE; a UA invitee still needs the verified-e-mail match.
- **Delegate inviter.** Authority follows `checkPermission` semantics: an invite created by a delegate acting for an Owner is valid while the delegation is active AND the delegate still holds an own active role in the org; revoking or expiring the delegation, or removing the delegate, invalidates it. Invites made by a legacy non-member delegate (possible before task 3b) become invalid at accept; that is the intended fail-closed reading.
- **Inviter deleted (FK).** `org_invites.invited_by` is NOT NULL with `ON DELETE CASCADE`, so deleting the user deletes the invite row and the token answers the existing bare 404. No code needed; a test pins it. If an invite row ever survives with a dangling `invited_by`, the id-based rule fails closed (`isActiveMember` false). The rule uses ids, never the `invitedBy` relation, so it cannot null-dereference.
- **No leak.** The new condition runs only after the invitee's verified-e-mail equality check, so any other account still gets the identical bare 404 whatever the inviter's state; the invitee sees the same "Invite link invalid or expired" page as for an expired invite.
- **Both modes.** The check is inside the controller and the routes are unmapped open routes (OPEN_ROUTES), so audit and enforce behave identically; a 404 is not a 403, so `DenialRecorder` writes nothing.
- **Not changed (deliberate).** `Auth\InviteController::register` and `show` (guest new-hire register link), `OrgAdminController::generateInvite`, `OrgInvite`, routes, `route_permission_map.php`, `route-list.json`, views, mail, migrations, config, `AuditFindingsRound2Test`. Parity for the guest link is an optional follow-up (ARCHITECTURE 12 item 13 below), NOT part of this amendment.
- **Residual race, accepted.** The check runs in `invitationFor()` before the claim transaction; an inviter removed in the same few milliseconds is not caught. It is MariaDB/concurrency territory and is named in ARCHITECTURE 12 item 4 (10.4).

#### 10.13.2 The fix (spec, not a patch)

Verified facts about the recorder: `App\Support\Rbac\DenialRecorder::record(Illuminate\Http\Request $request): void` is static and fail-soft (`try/catch` + `Log::error`, so a broken audit table can never turn a 404 into a 500). It does nothing without an authenticated user and is idempotent per request (attribute `rbac_denial_recorded`). If the middleware already wrote a `would_block` row for the request (audit mode only, attribute `rbac_audit_row`) it upgrades THAT row to `blocked` instead of inserting; otherwise it inserts one row: `outcome = blocked`, `reason = controller_denied`, `user_id` = the actor, `org_id` = `CurrentOrg::id`, and `method`, `route_uri`, `matched_pattern`, `permission_group`, `required_level`, `batch` resolved from `config/route_permission_map.php` by `METHOD uri`. It does not touch the response, and it behaves identically in audit and enforce mode and for JSON and browser requests (it only reads the request).

At each of the five sites, for the org-mismatch branch ONLY, call it immediately before the abort; controllers have no `Request` in these methods, so use the `request()` helper (as `AuditLog::event` already does). Add `use App\Support\Rbac\DenialRecorder;` to the three controller files. Pattern:

```
if ($userOrgRole->org_id !== $org->id) {
    DenialRecorder::record(request());
    abort(404);
}
```

| Site | Branch that gets the call | Branches that do NOT |
|---|---|---|
| `RfqController::authorizeRfq` | `(int) $rfq->org_id !== $orgId` | `$orgId === 0` (403, the renderer records it); the later hidden-project 404 (`Project::visibleTo(...)`, same org, pre-existing, wrote no row at HEAD either); the level 403 |
| `OrderApprovalController::authorizeApprovalAction` | `(int) $order->org_id !== (int) $orgId` | the `pending_approval` status 403 (the renderer records it) |
| `OrgAdminController::removeRole` | `$userOrgRole->org_id !== $org->id` | `! $org` 403; the level 403 |
| `OrgAdminController::destroyConnection` | `$orgRelationship->from_org_id !== $org->id` (this includes the counterpart org of 10.12.1) | `! $org` 403; the level 403 |
| `OrgAdminController::removeProjectMember` | `$projectMember->org_id !== $org->id` | `! $org` 403; the level 403s |

Why exactly one row per request: the renderer ignores 404, so there is no second call; `rbac_denial_recorded` makes any repeat a no-op; in audit mode with a below-level actor the middleware's `would_block` row is upgraded in place (no additional row), exactly as the old 403 path did; in enforce mode a below-level actor is stopped by the middleware (one `blocked` row, reason `no_grant`) and never reaches the controller. A missing id is a route-binding 404 before any controller and correctly writes nothing. Statuses, bodies and every 403 stay byte-for-byte as today (the existing `assertSame($missing->getContent(), $other->getContent())` assertions stay). The middleware 404s of B5 (project/quote routes) already write their own `blocked` row and are not touched. Rejected alternative: recording every 404 in the renderer; it would also log ordinary missing-record 404s all over the app (for example missing quote items) and change audit volume well beyond these five sites.

**Defect in the approved formula, found by the prototype.** Section 4 B2 / decision H1 says `seesAllOrgProjects = evaluate(userId, orgId, 'organization_management', 'F', null)`. `evaluate()` starts with step 0, `DelegationService::resolveEffectiveUserId`, so that literal formula (a) widens the LIST of every delegate of an Owner (`Project::visibleTo(delegate)` becomes the whole org, although the controllers scope by the logged-in id and ARCHITECTURE 12.3 says the delegate keeps his own list), and (b) makes delegation TRANSITIVE for project scope: `isActiveProjectMember($effectiveUserId)` would call `seesAllOrgProjects` with the principal, which resolves the principal's own delegation again, so D2 (delegation from D1) acting where D1 holds a delegation from the Owner passes project-scoped checks for every project. Today and in 10b "delegation is not transitive". Proven on the literal prototype: D2 `checkPermission(..., project_management, R, P2)` is true (must be false), D1 `projects/list` returns [P1, P2] (must stay [P1]). The existing suite cannot tell the two formulas apart (the same 20 cases fail with the literal and with the refined formula), so only the new tests of 10.14.6 T9 catch it.

**Final rule (code):**
- `PermissionService`: extract steps 1-2 of `evaluate()` (:93-107: active role ids of a user in an org, matrix level, rank compare) into `private function holdsLevel(int $userId, int $orgId, string $permissionGroup, string $requiredLevel): bool` that uses the given user's OWN roles and resolves no delegation. `evaluate()` keeps step 0 and calls `holdsLevel($effectiveUserId, ...)`; every existing result is byte-identical (the suite proves it). No constructor change (`ProjectCheckpoint2Test` builds an anonymous `PermissionService` subclass with the 3-argument constructor).
- New `public function seesAllOrgProjects(int $userId, int $orgId): bool` = `holdsLevel($userId, $orgId, 'organization_management', 'F')`. One short WHY comment is allowed here: own roles only, because resolving a delegation would widen a delegate's list (ARCHITECTURE 12.3) and make delegation transitive. No universal-admin logic inside (the callers keep theirs).
- `isActiveProjectMember($userId, $orgId, $projectId)`: first `if ($this->seesAllOrgProjects($userId, $orgId))` -> true iff a `projects` row exists with `id = $projectId`, `org_id = $orgId`, `deleted_at IS NULL`; otherwise the existing membership query, unchanged.

**Who gets it** (seed, from `role_permission_matrix.php`): `organization_owner`, `organization_admin`, `auditor_read_all`, `manufacturer_admin`, `platform_super_admin`, inside their OWN org only. Not: `estimator`, `project_manager`, `procurement_manager` (organization_management R), `executive_approver`, `financial_admin`/`budget_owner` (R), requisitioner, coordinator, viewer, superintendent. #### 10.14.12.1 V1 ruling (MEDIUM, must fix): RE-SCOPE, do not accept

Finding: `OrgAdminController::addProjectMember` (line 621) and `removeProjectMember` (line 650) load the project with `Project::where('org_id', $org->id)` and then rely on the engine alone (`requireProjectFull` = `checkPermission(Auth::id(), org, 'project_management', 'F', $project->id)`). `checkPermission` evaluates the EFFECTIVE (principal) user, and since W10 the principal Owner passes `isActiveProjectMember` for every project. What each role may CHANGE does not widen by itself: the Owner (full project, estimate, RFQ and procurement rights) can then edit, add members to, remove members from and delete (when empty) any project, edit any estimate and create or convert RFQs for any project; the Organization Admin can edit projects, delete empty projects and manage their members, but only read estimates and RFQs; the Auditor/Read-All can only read, which includes every estimate with its prices and every RFQ with the sellers' quoted prices in the organization; the Manufacturer Admin has no project or estimate rights, so it sees project names on RFQ pages, and project pages only while the platform runs in audit mode (enforce mode refuses them). Estimator, Project Manager, Procurement and every other role keep seeing only the projects they are a member of, and other organizations and sellers never see a buyer's project.
> 3. This reverses the rule in our architecture reference ("no owner bypass: an owner sees only the projects they are a member of") and departs from the project-membership scoping in the original RBAC implementation plan; it needs no data migration and can be withdrawn by reverting one release. The rule follows the permission matrix, not role names: anyone who may edit role permissions can give another role this visibility (a known open item, decision pending).
> 4. Please confirm in writing ("Approved: W10 as described"), and tell us: (a) whether the Auditor/Read-All, the Manufacturer Admin and the Platform Super Admin must also see every project of their organization, or must stay member-scoped; (b) whether the Auditor may read the sellers' quoted prices on RFQs of projects he is not a member of; (c) whether the Owner and the Organization Admin may delete empty projects they are not a member of.
