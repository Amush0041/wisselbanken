### F1. What I verified, and why N01-B stays

- QA's claim about effective authority is correct, checked against `database/seeders/Rbac/data/role_permission_matrix.php`: for every permission group held by Estimator, Procurement Manager or Executive Approver, the Organization Owner holds the group at the same or a stronger level. No group exists where one of the three outranks the Owner. So adding Estimator, Procurement Manager or Executive Approver to an active Owner adds no grant, which is exactly the property that makes D1 B defensible. The exemption is not an authority change; it only lets the roster show roles the Owner already covers.
- Routing and checks do not look at role names: `PermissionService::holdsLevel` uses the strongest level over the active rows; `ApprovalRoutingService::approverPool` is a DISTINCT user query on `role_permissions` (`approval_authority` F or A). Grep of `app`, `config`, `routes`, `resources`: no logic decides on the slug or name `executive_approver` / `procurement_manager`. A05 (`guardOwnOrder` -> `otherApprovers` -> `approverPool`) is untouched by the diff and stays pinned by the existing Q3 tests (own-order 403 with another approver, sole-approver `auto_approved`). Procurement Manager itself already holds `approval_authority` A, so even Procurement Manager + Executive Approver changes nothing in the pool.
- The authority that grows in QA's chain is step 1 (Estimator takes `organization_owner`), and step 1 is reachable without this round: `assignRole` checks `user_management` F, an active member target and `isAssignableByOrg` (the "Organization" category is assignable everywhere); nothing restricts who may grant `organization_owner`, including to himself. That is open item 6 (the seeded Estimator holds `user_management` F) and item 10, both "decision pending with the human". Reading before/after: step 2 used to be refused and is now allowed; the user's effective authority is the same either way.
- The one real difference: if the Owner row is removed later, the account keeps Estimator + Executive Approver (SoD never revokes a pair already held, as with the registration bundle). Documented in A2-T2.

### F2. Why accept

- The estimate flows are not transactional anywhere: `QuoteController` has no `DB::` call; `store` writes the quote, attachments, items, then the catalogue sync; `createFromList` and `duplicate` write items after `Quote::create`. Wrapping only enrol + `Quote::create` would not make creation atomic (a later item failure still leaves a quote without items); wrapping everything changes behaviour (stored files are not rolled back, the catalogue sync joins the transaction) and is a different task. The wrap is also not the smallest diff (a 20-line array at `store` becomes a closure with a six-variable `use` list).
- Membership does not depend on the estimate: `destroy` soft-deletes the quote and leaves the member; project creation enrols independently. "Enrolled, nothing created" is already a legitimately reachable state and the harmless direction. The reverse order (enrol after create) would allow "estimate exists, creator not a member", which breaks Mitch's sentence, so the plan's order stays.
- The stray state requires passing `creatableProject` / `writableQuote`, so it never grants access the caller lacked. If the wrap were ever wanted: the Quote model has no observers or create hooks (grep), `ProjectMember::enrol` already nests safely (it runs inside `ProjectController::store` and `RfqController::store` transactions), so a wrap would be a savepoint with no side effect moved. It is just not worth it.
